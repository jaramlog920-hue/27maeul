# 경제·필사·진행·제작·여행·시설 재감사 — 2026-10-19 round 2

현재 소스에서 **확정한 기능 오류는 Low 3건**이다. 이전 E08 도구 구매 재화 손실과 E02 작업장 주인 혼동은 최신 소스로 다시 실행하여 수정됨을 확인했다. 범위를 채우기 위해 의도가 명시된 동작을 버그로 만들지 않았다. 수납 한도 초과 시 손실 2건은 실제 관찰했으나, 공통 `stash`의 명시적 버림 정책과 충돌 여부를 정할 근거가 부족하여 확정 결함 수에 넣지 않았다.

기존 소스·기존 테스트·설정·데이터는 수정하지 않았다. 새 파일은 이 감사 폴더에만 썼다. 실사용 세이브·외부 전송·결제·삭제는 실행하지 않았다.

## 확정 오류 (같은 심각도 내 재현 영향 순)

### E-R2-01 — Low — 배운 제작법이 재료 소모로 생기는 빈칸을 고려하지 않아 제작을 막음

- **유형:** 기능 오류 / 경계값 / UI와 제작 결과 공간 계산 불일치.
- **위치:** `src/engine/skills.ts:110`–`:115`, 특히 `:112`는 `useStock` 전 원래 가방에 결과가 들어가는지 검사한다. `src/features/skills/SkillLesson.tsx:100`·`:107`도 같은 원래 상태로 제작 버튼을 끈다. 일반 제작의 `src/engine/game.ts:3687`은 재료 차감 후 상태로 검사하므로 이 경로만 다르다.
- **원인:** 지급 가능성을 재료 사용 이전에 계산한다.
- **발생 조건·재현:** 목수 마감법을 배운 뒤, 갈대가 정확히 2개 있는 가방을 서로 다른 물건 50칸으로 채우고 의자는 갖지 않은 상태에서 제작 화면을 연다. 갈대 2개를 쓰면 해당 슬롯이 비어 의자 1개가 들어갈 수 있지만 만들기 버튼이 비활성이고 `craftLearned`도 원래 상태를 반환한다.
- **실제 검증:** React/jsdom 버튼 및 실제 엔진으로 **재현 완료**. 목수 의자·방석·과일 그릇·바구니·말린 꽃 5개 제작법 모두 확인했다. 재료 차감 시 슬롯은 49개(과일 그릇은 48개)이고 `overflows(paid, output) === false`다. 제작과 무관한 물건 한 종류를 미리 비운 대조군은 결과 1개를 정상 지급했다.
- **실행 증거:** `round2.test.ts`의 `learned craft ...` 5개 테스트, `runtime-results.json`; `R2_CRAFT_FALSE_FULL {"id":"carpenterFinish","slotsBefore":50,"slotsAfterPayment":49,"rejected":true,"controlDelivered":1}` 등.
- **영향:** 배운 기술의 개인 제작. 재료·결과를 잃지는 않으며 불필요한 물건 정리로 복구 가능하다.
- **권장 수정:** 공통 제작 가능 함수에서 `paid = useStock(...)`을 먼저 계산하고 그 상태의 `overflows`로 UI와 엔진을 함께 판정한다. 부족한 재료/공간은 원래 상태를 보존한다.

### E-R2-02 — Low — 식탁을 옮기면 자리 대표 좌표가 남아 주변 손님 판정이 달라짐

- **유형:** 데이터 일관성 / 기능 간 충돌 / 저장 전후 상태 차이.
- **위치:** `src/engine/spaces.ts:175`–`:183`, 특히 `:181`은 가구 ID만 바꾸고 `HomeSpace.at`은 그대로 복사한다. `src/engine/game.ts:5055`–`:5062`도 새 공간 ID와 차려 둔 식탁 ID만 갱신한다. 소비자는 `src/engine/cooking.ts:265`–`:278`에서 옛 `sp.at`을 중심으로 반경 4칸 이웃을 고른다. 저장 복원의 `src/engine/spaces.ts:186`–`:194`·`:198`–`:211`은 새 가구에서 대표 좌표를 다시 계산한다.
- **원인:** 가구 좌표/자리 이름표/식탁 참조는 옮기면서 자리 대표 좌표는 동기화하지 않는다.
- **발생 조건·재현:** 생활방의 탁자 `(9,112)`와 의자 `(10,113)`, `(11,113)`를 차 자리로 지정하고 두 접시를 차린다. 의자와의 거리를 유지하며 탁자만 `(11,112)`로 옮긴다. 이웃이 `(14,112)`에 있을 때 손님 후보를 비교한다.
- **실제 검증:** 실제 `placement`·`designateSpace`·`serveTable`·`moveFurniture`·`settleTable`·`dinersNear`·serialize/deserialize로 **재현 완료**. 이동 뒤 식탁은 유효하고 2접시가 남지만, 공간 ID는 `space:table:11:112`인데 `at`은 `(9,112)`다. 손님 목록에 baker가 없고, 같은 가구·같은 NPC 좌표에 대표 좌표 정리만 적용된 불러오기 대조군에는 baker가 있다. NPC 위치는 저장하지 않으므로 대조군에서 동일 위치를 명시적으로 유지하여 이 변수와 좌표 정리의 효과를 분리했다.
- **실행 증거:** `R2_MOVED_TABLE {"space":{"id":"space:table:11:112","use":"tea","at":{"x":9,"y":112},"furniture":["table:11:112","chair:10:113","chair:11:113"]},"beforeReload":[],"afterReload":["baker"],"loadedAt":{"x":11,"y":112}}`.
- **영향:** 옮긴 차 자리의 주변 식사 초대 후보와 대표 위치 표시. 실제 모바일/브라우저 NPC 이동을 수동 재현한 것은 아니다.
- **권장 수정:** 이동 완료 후 새 가구 배치에서 공간의 대표 좌표도 다시 계산한다. 공간/식탁 ID 변경과 같은 상태 변경에서 처리해 저장 전후가 일치하도록 한다.

### E-R2-03 — Low — 수납 가구의 궤짝을 텃밭 수확만 인정하지 않음

- **유형:** 기능 간 충돌 / 동일 저장소의 사용 가능성 불일치.
- **위치:** `src/engine/garden.ts:52`–`:62`, 특히 `:57`은 `unlock:supplyChest` 표식만 본다. 반면 `src/engine/game.ts:3607`–`:3610`의 `chestOf`는 빵 보관장·이불장·서랍장 등 `use === 'open'` 가구도 같은 궤짝으로 인정한다. `src/store/game-store.ts`의 `harvestAt`은 이 불일치의 실패를 가방 가득 안내로 표시한다.
- **원인:** 수확이 공통 수납 판정 대신 이전의 해금 표식 검사를 직접 구현한다.
- **발생 조건·재현:** 정식 재료 궤짝 해금 표식 없이 빵 보관장(`breadCupboard`)을 집에 둔다. 공통 궤짝은 비워 두고 가방 50칸을 채운다(약초 슬롯 없음). 다 자란 약초를 거둔다.
- **실제 검증:** 실제 생산 함수로 **재현 완료**. `chestOf(game) === {}`, 공통 `overflows(game,{herb:2}) === false`, `putAway`는 궤짝에 약초 2개를 넣지만 같은 상태의 `harvest`는 null이다. `unlock:supplyChest` 표식만 더한 대조군은 같은 궤짝에 2개를 넣고 수확한다.
- **실행 증거:** `R2_GARDEN_STORAGE {"genericChestUsable":true,"genericOverflow":false,"harvestRejected":true,"withRedundantUnlockDelivered":2}`.
- **영향:** 수납 가구만으로 궤짝을 사용하는 사람의 가방 만원 수확. 작물은 남고 물건을 비우면 수확할 수 있다.
- **권장 수정:** 수확도 공통 궤짝 접근 판정을 사용한다. 순환 의존을 피하려면 가구/해금 기반 수납 가능성을 순수 공통 함수로 분리한다.

## 확정 결함에서 제외한 실제 동작 관찰

공통 `src/engine/easier.ts:83`은 궤짝이 없거나 차면 넘치는 물건을 버리는 정책을 명시한다. 아래는 손실이 실제로 일어난다는 증거이며 그 정책 자체를 바꿔야 한다고 확정한 버그가 아니다.

- **여행 보상:** 현재 실제 `tripSeed`와 전체 `playTurn`으로 나온 8일 항구 여행의 보상은 꿀 2개·봉인용 밀랍 1개다(씨앗 568368090). 가방 50칸, 빈 슬롯 없음/궤짝 없음이면 UI 귀환 버튼이 활성이고 귀환 후 두 보상 모두 0개다. 75닢은 정상 차감되어 1,000→925닢, 날짜는 9일이 된다. 빈 가방 대조군은 같은 보상을 모두 받는다. `game.ts:3287`–`:3288`은 구매만 검사하고 `:3322`의 보상은 `putAway`로 버려진다. 정책이 의도된 것이라도 보상 수확 화면에 공간 부족/버림 안내가 없어 사용자가 기대를 오해할 위험이 남는다. 귀환 자체를 가방 조건으로 막으면 여행 중 갇힐 수 있으므로 그런 수정을 권하지 않는다.
- **자동 잉크 항아리:** 물 3개와 다른 물건 49종, 궤짝 없음, 푸른 염료 없음에서 아침 생산 3회 결과가 `(물2,염료0)→(물1,염료0)→(물0,염료1)`이다. `game.ts:4947`–`:4949`는 받을 공간을 확인하지 않고 물을 쓴다. 물이 없어지며 그 슬롯이 비는 마지막 날에만 염료가 들어간다. 앞의 두 생산분은 명시된 넘침 버림 정책에 해당한다. 가득 찼을 때 생산을 쉬게 할지/현재 정책을 알릴지는 제품 규칙 확인 사항이다.

## 테스트 실행 결과

`round2.test.ts`만 실행한 최신 결과는 **14/14 통과, 12.70초**다. 가방 크기 0/49/50/51, 궤짝 없음/0/29/30, 수량 1/2/30/99/100의 **80조합**도 이 안에서 실행했다. 넘침 검사와 실제 지급 수량의 불일치를 발견하지 못했다. 실패 재현을 단언하는 테스트의 통과가 결함 없음이라는 뜻은 아니다. 콘솔의 canvas 미구현 경고는 jsdom의 한계이며 UI 이벤트·스토어 단언은 완료됐다.

초기 감사 하네스에서 집 바깥 좌표, 저장 시 재생성되는 NPC 위치, 재료가 없는 주사위 씨앗을 잘못 전제한 케이스를 고쳤다. 이는 테스트 전제 교정이며 프로덕션 수정은 없었다. 최종 결과는 `runtime-results.json`에 있다.

전체 기존 테스트 중 요청받은 `review-probes.test.ts`·`CopyAgain.test.tsx`는 감사 전용 import 진입점으로 독립 재실행했다. 원본 8개 중 2개 실패가 재현됐다. 두 실패 모두 최신 정책을 반영하지 못한 테스트 전제였고, 같은 기능의 정책에 맞춘 대조군 **2/2가 통과**했다. 상세 근거는 `TEST_TRIAGE.md`, `triage-results.json`, `triage.log`를 참조한다. 기존 파일은 고치지 않았다.

## 검사 대상·완료 범위·강도

- 기존 담당은 엔진 78개+UI/support 63개 = **141개 독립 파일**, 공유 `game.ts`·`game-store.ts` 관련 선언·함수·호출부다.

## 남은 한계·우선순위

우선 수정 후보는 UI·엔진 판정이 함께 잘못된 배운 제작법과 텃밭 수납 공통화다. 그다음 공간 대표 좌표 동기화로 저장 전후의 손님 판정을 맞춘다. 모두 현재 Low로 분류했으며, 데이터가 사라지거나 진행이 영구히 막히는 재현은 이 세 건에서 없었다.

실제 브라우저·모바일 장치·물리 IME/마이크/음성 합성은 이 담당자가 실행하지 못했다. jsdom은 실제 NPC 이동·음성 서비스·canvas 메모리를 검증하지 않는다. 모든 가능한 세이브·조작 순서·확률 씨앗을 전수 탐색하지 않았고, 검사 강도를 구분했다. 오류를 못 찾은 기능에 오류가 없다고 보장하지 않는다.
