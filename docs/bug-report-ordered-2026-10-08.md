# 27마을 — 1~31번 순서 버그 점검

2026-10-08 로컬 작업 폴더 기준. **플레이·저장 문제 20건과 빌드 차단 1건**을 정리했다. 같은 원인의 여러 증상과 다른 보고서의 중복은 한 건으로 묶었다. 게임 구현은 수정하지 않았으며, 이 보고서·진단 검사·검사 결과만 추가했다.

엔진 API, 저장 왕복, React/jsdom 대화창·식탁 화면으로 재현했다. 기존 가족·동물 보고서의 검사도 현재 코드에서 다시 실행했다. 실제 사용자 저장, 휴대폰 터치, 소리 재생, 캔버스 화소를 직접 확인한 결과는 아니다. 다른 작업에서 코드가 계속 변경되고 있어 **재현 실행 02:58:27 KST**, 빌드 실행 약 03:00 KST의 결과를 기준으로 한다. 위치는 줄 번호보다 함수 이름을 함께 참고한다.

P1은 진행 차단·관계/위치 손상·빌드 차단, P2는 기능·기록 오류, P3은 표시 오류·제한된 입력 손상·설계 기능 누락이다. ‘추가 확정 없음’은 아래 검토 범위에서 새 결함을 확정하지 않았다는 뜻이다.

## 버그 상세 — 같은 번호 순서

### 1. 저장·불러오기

**01-A [P2] 자동 저장에서 추가한 업적·도감이 실행 중 상태에 반영되지 않는다.**

- 재현: 업적이 비어 있는 닢 500 상태에서 모달을 열고 `frame(20)`으로 자동 저장을 실행한다.
- 실제: 저장 본문에는 `coins500`이 있지만 실행 중 `game.achieved`에는 없다. 다시 기록 계산하면 같은 업적을 또 새 업적으로 판정한다. 창 숨김/닫기의 `saveGame(실행 중 상태)`는 빠진 기록으로 덮어쓸 수 있다.
- 원인: [game-store.ts](../src/store/game-store.ts)의 `persist`는 `recordProgress` 결과를 반환하지만 `frame`의 20초 저장 호출은 반환값을 버린다. 이후 tick도 이전 `s.game`을 사용한다. 창 종료 저장은 [Play.tsx](../src/features/play/Play.tsx)의 `save`.
- 수정 방향: 저장에 사용한 기록 상태를 store와 같은 프레임의 계산에 반영한다. 일반 진행·모달·꾸미기·여행 중 분기를 함께 확인한다.

**01-B [P3] 옛 ID 마이그레이션이 현재 저장의 사용자 글도 바꾼다.**

- 재현: ‘나의 한 줄’에 `innkeeper, lambFound: 내가 직접 쓴 메모`를 넣고 현재 버전으로 저장·불러오기한다.
- 실제: `apothecary, lambClover: 내가 직접 쓴 메모`로 바뀐다. 해당 영문 문자열을 포함할 때 발생하며 모든 한국어 메모가 변하는 문제는 아니다.
- 원인: [save.ts](../src/engine/save.ts)의 `deserialize`가 JSON 파싱 전에 저장 전체 문자열에 `.replace(/innkeeper/g, ...)` 등 ID 치환을 적용한다.
- 수정 방향: 파싱 후 식별자 필드와 필요한 키만 이전하고 사용자 입력 값은 보존한다.

### 2. 이동·상호작용

**02-A [P2] 새 터 책상을 스페이스·조이스틱으로 열 수 없다.**

- 재현: 새 터 서고 책상 `(16,32)` 앞 `(16,33)`에서 위를 바라본다. 클릭·스페이스·조이스틱 상호작용을 비교한다.
- 실제: 클릭은 `otDesk` 표적을 찾지만 `interactTile`은 `null`, `pressTile`은 책상 대신 현재 칸 `(16,33)`을 반환한다.
- 원인: [game.ts](../src/engine/game.ts)의 `interactableAt`은 왕래 표식을 제외한 새 터 칸에 바로 `false`를 반환한다. 클릭의 새 터 장소 판정이 앞칸 판정에 연결되지 않았다.
- 수정 방향: 새 터 책상·책장·시설의 판정을 입력 방식들이 공유하도록 연결한다. 직접 재현한 장소는 서고 책상이다.

### 8. 필사 퍼즐

**08-A [P2] 책을 바꾸면 이전 장의 퍼즐·오타 기록을 잊는다.**

- 재현: 마태복음 1장 첫 절을 퍼즐로 쓴다 → 마가복음 한 절도 퍼즐로 쓴다 → 마태복음으로 돌아와 나머지 절을 직접 쓴다.
- 실제: 전체 직접쓰기 장에만 줄 정성 도장이 `careDone: ['mt:1']`로 지급된다. 이전 장의 퍼즐 절 수·수고 비율도 잃을 수 있다.
- 원인: [copy-ways.ts](../src/engine/copy-ways.ts)의 `CopyCare`가 책·장 키 하나만 보관한다. `careFor`는 다른 키이면 오타 0·퍼즐 없음으로 새 기록을 만들고, [game-store.ts](../src/store/game-store.ts)의 `copyPuzzle`/`commitVerse`가 그것을 사용한다.
- 수정 방향: 미완료 장의 기록을 책·장별로 보관하고 완료한 장만 정리한다. **같은 장의 `puzzled` 저장 소실은 이미 수정되어 이번 왕복 검사는 통과했으며 이 문제와 별개다.**

### 14. 요리·식사

**14-A [P3] 마지막 접시를 먹으면 반응에 다른 요리 이름이 나온다.**

- 재현: 식탁에 무화과 간식 접시 2개를 차리고 파피와 함께 먹어 모두 비운다.
- 실제: 화면은 ‘파피 · **꿀 곁들인 빵** 쪽으로 … 맛을 봐요.’로 표시한다. 식탁 재고 차감은 정상이다.
- 원인: [CookingView.tsx](../src/features/cooking/CookingView.tsx)의 반응은 현재 `c.table?.item`을 읽고 식탁이 없으면 `honeyBread`를 쓴다. 반응 상태에는 먹었던 음식이 없다.
- 수정 방향: 식사 결과에 실제 음식 ID를 함께 보관해 반응에 사용한다.

### 17. 의뢰·일·능력치

**17-A [P2] 새 주민이 이사 오면 이미 게시된 부탁의 주민이 바뀐다.**

- 재현: 10일의 게시판 목록을 읽는다 → 목수 이사 표식 `movedIn:carpenter`를 켠다 → 같은 날 목록을 다시 읽는다.
- 실제: 같은 부탁 ID `5:0`이 기름틀 주민 → 우편 주민으로, `7:1`이 포도원 할아버지 → 대장장이로 바뀐다. 완료 표식은 같은 ID에 연결되어 있다.
- 원인: [game.ts](../src/engine/game.ts)의 `copyRequestsToday`가 현재 주민 풀을 만들고 [copy-requests.ts](../src/engine/copy-requests.ts)가 그 풀로 지난날의 부탁까지 매번 다시 생성한다. ID는 날짜·순번이고 NPC는 풀의 인덱스로 정해진다.
- 수정 방향: 게시 시점의 부탁을 고정해 저장하거나, 주민 풀의 변화가 지난 부탁의 정체성을 바꾸지 않도록 생성 규칙을 바꾼다.

### 19. 연애·결혼·헤어지기

**19-A [P1] 주민 배우자가 있는 대상에게도 플레이어가 고백할 수 있다.**

- 재현: 실제 주민 결혼 API로 루디–파피 부부를 만든다. 여자 모습 플레이어가 루디 하트 10개·들꽃 다발 1개·연인 없음 상태에서 고백한다.
- 실제: 고백이 허용되어 플레이어 연인이 `rudy`가 된다. 주민 계보의 `rudy.spouse = poppy`도 남아 중복 관계가 된다.
- 원인: [game.ts](../src/engine/game.ts)의 `canGiveBouquet`가 주민 배우자를 확인하지 않는다. [gen-relations.ts](../src/engine/gen-relations.ts)의 `releasePlayerPartner`도 배우자 관계를 제거하지 않는다.
- 수정 방향: 대상의 실제 현재 인물·주민 배우자·플레이어 관계를 함께 검사한다. 기존 가족 보고서 F01과 동일하며 재검증에서도 실패했다.

### 22. 주민 가족·세대교체

**22-A [P2] 자녀가 결혼하면 가계도에서 원래 부모와의 연결이 숨겨진다.**

- 재현: 결혼 전 아서(`carpenter`) → 루디 연결을 확인한다 → 루디–파피 결혼 → 가계도를 다시 계산한다.
- 실제: `rudy.parents = ['carpenter']`는 남지만 화면용 `familyGroups`에는 아서 → 루디가 없다.
- 원인: [gen.ts](../src/engine/gen.ts)의 `familyGroups`가 신혼 가구에 나온 사람을 `used`로 표시하고, 기존 가구의 자녀를 `used` 기준으로 제외한다.
- 수정 방향: 카드 중복 제거와 부모–자녀 연결 보존을 구분한다. 기존 가족 보고서 F02.

**22-B [P2] 실제 방과 연결되지 않은 신혼집 때문에 아기가 표시되지 않는다.**

- 재현: 루디–파피 결혼 → 침대 건네기 → 출생일까지 정산한다.
- 실제: 아기 `g-0001`은 가계도·가구 목록에 있지만 첫 마을 모든 `ROOMS`의 `householdBabies` 결과에는 없다.
- 원인: [gen-settle.ts](../src/engine/gen-settle.ts)의 `homeOfFor`는 주민 ID만 가족의 집으로 인정한다. 파피의 가족 집 `teahouse`는 방 소유자지만 주민 ID가 아니므로 존재하지 않는 `poppy` 방을 거주지로 저장한다. [village-followup-scene.ts](../src/render/village-followup-scene.ts)는 `h.home === room.owner`로 아기를 찾는다.
- 수정 방향: 실제 방 소유자·상속된 거주지를 기준으로 집을 연결하고 표시 가능한 임시 거처를 둔다. 기존 가족 보고서 F03. 새 터 주택 희망 기능 추가 후에도 이 재현은 남는다.

**22-C [P1] 부모 자리를 이어받은 자녀의 결혼·출산 연결이 끊긴다.**

- 재현: 루디–파피, 웬델–틸리의 아이를 출생·성장·견습·은퇴·이사까지 정산한다. `canPair`가 허용하는 후계자 둘을 준비한다.
- 실제 A: 파피 자리에 후계자 이름은 나오고 엔진의 결혼 상담도 존재하지만 ‘이야기 들어 주기’ 단추가 없다. 필수 상담 응원을 할 수 없어 진행이 막힌다.
- 실제 B/C: 이후 단계를 별도 상태로 준비하면 결혼식 두 NPC가 결혼 자리에 가지 않고, 후계자 부부에게 ‘아기 침대 건네기’ 단추도 없다.
- 원인: [TalkBox.tsx](../src/features/talk/TalkBox.tsx)는 부모 자리 ID를 [GenTalk.tsx](../src/features/talk/GenTalk.tsx)에 넘긴다. 상담·준비·침대는 생성 인물 ID(`g-0001` 등)에 연결되어 있다. [game.ts](../src/engine/game.ts)의 결혼식 특별 자리도 생성 ID를 쓰지만 실제 NPC 객체는 부모 자리 ID다.
- 수정 방향: 자리 ID와 현재 인물 ID 변환을 대화·행사·호감도·이름 표시에 일관되게 적용한다. 기존 가족 보고서 F04. B/C는 A를 실제 플레이로 통과했다는 주장이 아니라 뒤 단계의 독립 재현이다.

**22-D [P2] 주민 정원이 차면 출생 예약이 대기 대신 삭제된다.**

- 재현: 침대를 이미 건네 출생일이 잡힌 가구를 준비한다. 출생일에 생성 주민 8명으로 정원이 찬 상태를 정산하고 저장·불러오기한다.
- 실제: `cribAsk.given = true`만 남고 `birthDue`가 지워진다. 첫 아이도 없어 첫 출생을 다시 예약할 경로가 사라진다.
- 원인: [gen-birth.ts](../src/engine/gen-birth.ts)의 `settleBirth`는 정원 초과와 가구 자녀 상한을 같은 취소 분기로 처리한다. [구현 계획 D14·작업 13](superpowers/plans/2026-10-06-plan-20-ot-village-and-generations-build.md)은 정원에서 대기를 명시한다.
- 수정 방향: 정원 초과는 예약을 유지하고, 이미 자녀 상한을 채운 경우와 구분한다. 기존 가족 보고서 F07과 동일.

### 23. 동물 친구·동행

**23-A [P1] 새 터에서 따라오기를 누르면 첫 마을 동물 좌표가 손상된다.**

- 재현: 동물을 집에 둔다 → 새 터 서고로 간다 → 가족 메뉴에서 데리고 다니기 → 첫 마을로 돌아온다.
- 실제: 동물이 집 `(19,114)` 대신 새 터 서고 좌표 `(19,37)`를 첫 마을 좌표로 사용한다. 해당 칸은 막혀 있고 귀환 후 200 tick(10초)에도 동물이 갇혀 있다. 기록자와 거리 46칸.
- 원인: [game.ts](../src/engine/game.ts)의 `setCompanionStay(false)`가 현재 지도의 기록자 옆 칸을 동물에 넣는다. 동물은 첫 마을에 남는 설계인데 지도 검사가 없다. [Family.tsx](../src/features/family/Family.tsx)의 명령은 새 터에서도 열려 있다.
- 수정 방향: 명령 가능 지도·동물 위치의 지도 기준을 맞춘다. 기존 동물 보고서 1번.

**23-B [P2] 가구가 있는 옆 칸을 목표로 골라 동물이 따라오지 못한다.**

- 재현: 집 `(18,114)`에 합법적으로 작은 의자를 놓고 기록자는 `(18,113)`, 동물은 집 입구 `(20,114)`에 둔다. 다른 인접 빈 칸으로 가는 경로가 존재한다.
- 실제: 100 tick(5초) 후에도 동물은 입구에 있고 거리 3칸이다. 가까이 있어야 하는 동물 활동도 막힌다.
- 원인: [companion.ts](../src/engine/companion.ts)의 `companionGoal`이 가구 blocker 없이 의자 칸을 고른다. [game.ts](../src/engine/game.ts)의 이동에서 길찾기는 실패하지만 대체 목표를 고르지 않는다.
- 수정 방향: 목표를 고를 때부터 blocker·도달 가능성을 고려한다. 기존 동물 보고서 2번.

**23-C [P2] 내 집 이외 건물에 동물이 함께 들어오거나 나오지 못한다.**

- 재현: 동행 중 첫 마을 서고로 들어간다. 별도로 실내 가족 메뉴에서 따라오기로 동물을 데려온 뒤 문깔개로 나간다.
- 실제: 들어갈 때 기록자 `(36,57)` / 동물 바깥 `(23,8)`. 나갈 때 기록자 바깥 `(24,8)` / 동물 실내 `(36,56)`. 10초 후에도 동물이 실내에 남는다.
- 원인: [game.ts](../src/engine/game.ts)의 `enterDoor`는 기록자만 옮기고 tick의 동물 동반 워프는 `homeWarp`에만 적용된다. 분리된 방은 걸어서 연결되지 않는다.
- 수정 방향: 일반 건물 출입도 동물 동행 상태와 연결한다. 실내 출입을 제한할 의도라도 메뉴로 들어온 동물은 나올 수 있어야 한다. 기존 동물 보고서 3번의 입장·퇴장 재현을 한 건으로 묶었다.

**23-D [P3] 새 목표에 이미 도착해 있어도 옛 경로를 계속 걷는다.**

- 재현: 동물 `(12,18)`의 경로가 `(12,19) → (12,20)`일 때 기록자가 돌아와 새 목표를 현재 동물 칸 `(12,18)`으로 바꾼다.
- 실제: 0.25초 뒤 동물은 `(12,19)`로 더 멀어지고 옛 경로도 남는다.
- 원인: [companion.ts](../src/engine/companion.ts)의 `stepCompanion`이 새 목표와 현재 칸이 같을 때 지난 path를 비우지 않는다.
- 수정 방향: 현재 칸이 새 목표이면 옛 경로를 취소한다. 기존 동물 보고서 4번.

### 25. 집 확장·가구 꾸미기

**25-A [P2] 배운 가구 마감이 불러오기·회전 때 사라진다.**

- 재현: 목수에게 배운 따뜻한 마감 선택(`skillFinish:stool = 2`)으로 집 `(18,114)`에 작은 의자를 배치한다. 저장·불러오기와 가구 회전을 각각 실행한다.
- 실제: 처음 놓았을 때 `finish = 'warm'`이지만 두 경로 모두 `undefined`가 되어 기본 모습으로 돌아간다.
- 원인: [room.ts](../src/engine/room.ts)의 `refitRoom`은 `placement`가 재생성한 기본 필드만 보관한다. `rotation`도 새 placement만 반환하고 [game.ts](../src/engine/game.ts)의 `rotateFurniture`가 그대로 교체한다. `finish`를 이어 붙이지 않는다. 새 터 방의 `sanitizeRooms`도 같은 refit 경로를 사용한다.
- 수정 방향: 배치 검증으로 재계산해야 하는 좌표·방향과 보존할 장식 메타데이터를 구분한다. 의자의 두 실제 경로를 재현했고, 다른 기술 가구·새 터 방도 함께 회귀 확인할 대상이다.

### 27. 손님집·손님 입주

**27-A [P2] 빈집 주민 자리의 나무를 그대로 둔 채 손님을 입주시킨다.**

- 재현: 손님집과 아래 방향 빈 입주 주택 `(16,12)`을 완공한다 → 빈집 주민 자리 `(19,16)`에 작은 나무를 정상 건축한다 → 이전 방문 선물을 준 넬리를 재방문 때 입주시킨다.
- 실제: 나무 칸은 걷지 못하지만 입주가 허용되어 `settled:nelly = 2`가 생긴다. 주민 칸을 눌러도 경로는 인접 칸으로 끝나며 도착한 칸의 시설 판정에 주민이 없어 입주 대화가 열리지 않는다.
- 원인: [newland-build.ts](../src/engine/newland-build.ts)의 `canPlace`는 이미 사람이 사는 home의 주민 자리만 보호한다. [newland-life.ts](../src/engine/newland-life.ts)의 `freeHome`/`canInviteGuest`는 빈집 주민 자리의 장애물을 확인하지 않는다. [game-store.ts](../src/store/game-store.ts)의 `arrive`는 실제 도착 칸으로 `facilityAt`을 조회한다.
- 수정 방향: 빈집 자리도 미리 보호하거나 입주 시 안전한 주민 자리·접근 경로를 검증한다. **기존 ‘입주 후 주민 자리에 나무 건축’은 수정됐다. 이 건은 입주 전에 둔 나무로 발생하는 별도 경계 사례다.**

### 29. 일지·앨범·도감·업적

**29-A [P2] 현재 게시판 부탁으로 ‘게시판 단골’ 업적을 달성할 수 없다.**

- 재현: 현재 게시판이 사용하는 `writeRequest`로 부탁 10개를 완료하고 업적을 계산한다.
- 실제: `req:` 완료 표식은 10개지만 `board10` 업적이 없다.
- 원인: [achievements.ts](../src/engine/achievements.ts)의 `board10`은 예전 의뢰 `board:` 표식만 센다. 현재 [BoardView.tsx](../src/features/talk/BoardView.tsx)는 `writeRequest`를 사용하며 그 경로는 `req:`를 기록한다.
- 수정 방향: 현재 부탁 완료를 업적 조건에 연결하고, 이전 저장의 예전 의뢰 횟수도 호환되게 처리한다. 다른 재료 요청도 `req:` 접두어를 쓰므로 단순 접두어 합산으로 잘못 포함하지 않도록 구분한다.

### 30. 화면·설정·소리 / 실행 검증

**30-A [P1] 현재 콘텐츠 문구 때문에 `npm run build`가 prebuild에서 중단된다.**

- 재현: 현재 작업 폴더에서 `npm run build` 실행.
- 실제: `life-text.newlandLife.kidWork.mile10`의 ‘이제 아침에 문을 열면 **누가** 먼저 올지 알 것 같아요.’가 금지어 `(?<![가-힣])누가(?!복음)`에 걸린다. `verify-pieces` 오류 1개로 종료하여 TypeScript·Vite 빌드까지 진행하지 않는다.
- 원인: [life-text.json](../src/content/life-text.json)의 일반 의문 대명사 ‘누가’도 [forbidden.ts](../src/content/forbidden.ts)의 인물 이름 검사와 충돌한다. [verify-pieces.mjs](../scripts/verify-pieces.mjs)는 모든 생활 문구에 이를 적용한다.
- 수정 방향: 기존 콘텐츠 규칙에 맞게 대사를 조정하거나 검증의 의도와 일반 단어 판정을 구분한다. 배포 빌드가 통과하는지 재확인한다. 단순 경고 43개와 이 오류 1개를 구분한다.

### 31. 캐릭터 그림·애니메이션

**31-A [P2] 손주 세대에 부모의 외형이 전달되지 않는다.**

- 재현: 생성된 자녀 둘을 결혼시키고 침대를 건넨 뒤 손주 출생을 정산한다.
- 실제: 부모에게는 피부·앞머리·뒷머리·윗옷·아랫옷 5개 외형 값이 있지만 손주에게는 `avatar`가 없다. 표시 시 기본 외형으로 돌아간다.
- 원인: [gen-settle.ts](../src/engine/gen-settle.ts)의 `avatarOfFor`가 고정 `CONTENT.neighbors`만 찾아 생성된 부모의 `gen.persons[id].avatar`를 조회하지 않는다.
- 수정 방향: 생성 인물의 저장 외형을 우선 조회한다. 기존 가족 보고서 F05. 22-C 이후의 출생 경로를 엔진으로 독립 검증했다.

**31-B [P3 · 설계 누락] 자녀 머리색이 부모와 무관하게 기본색이다.**

- 재현: 루디–파피의 자녀를 출생시키고 표시용 머리색을 비교한다.
- 실제: 부모 색은 HSV `[15,60,40]`, `[5,55,45]`지만 아이는 기본 `[25,62,35]`다.
- 원인: [gen-settle.ts](../src/engine/gen-settle.ts)의 `avatarOfFor`는 정수 외형 번호 5개만 전달한다. [gen.ts](../src/engine/gen.ts)의 외형 타입·저장 검증과 [gen-looks.ts](../src/engine/gen-looks.ts)도 색 배열을 연결하지 않는다.
- 판정: [구현 계획 작업 13](superpowers/plans/2026-10-06-plan-20-ot-village-and-generations-build.md)의 부모 ‘머리·피부·색 조합’ 요구에 대한 기능 누락이다. 런타임 예외와 구분한다.
- 수정 방향: 색 값을 출생 조합·외형 타입·저장·표시까지 연결한다. 기존 가족 보고서 F06.
